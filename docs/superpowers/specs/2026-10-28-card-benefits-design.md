# 쇼핑몰별 카드 혜택 설계 (1단계)

작성 2026-10-28. 브레인스토밍 대화에서 확정한 내용과 작성자(Claude)의 결정을 구분해 적는다.

## 의도

핫딜 허브의 최종 모습은 "핫딜 + 그 쇼핑몰에서 지금 혜택을 주는 카드"를 보여 주는 정보 사이트(나중엔 앱)다. 방문자는 **이미 가진 카드** 중 무엇으로 결제할지 고른다. 카드 발급 유도와 수수료는 없다.

이번 1단계는 그 중심 데이터인 **쇼핑몰 × 카드 혜택 표**를 만들어, 지금 운영 중인 상품권 딜 페이지에 붙이는 것이다. 2단계(일반 핫딜 수집 확장)와 3단계(주간 카드 행사 수집·내 카드 저장·웹앱)는 이 표를 재사용한다.

## 배경 사실 (2026-10-28 조사)

- 사용자가 내려받은 카드고릴라 크롤(로컬 PC의 `26.10.28카드고릴라\output\api` 폴더, 저장소 밖)에 판매중 카드 1,210건의 상세 JSON(전월실적·연회비·핵심혜택·유의사항 전문)이 있다.
- 카드 유의사항 대다수가 **상품권·기프트카드·선불충전 구매를 실적과 혜택에서 제외**한다. 따라서 상품권 딜에는 "이 쇼핑몰 할인 카드"를 그대로 붙이면 틀린 안내가 된다. 일반 상품에는 이 제외가 적용되지 않는다.
- 카드고릴라는 등록된 금융상품판매대리·중개업자다. 그 문구·이미지·분류를 공개 사이트에 재게시하면 데이터베이스권·이용약관 위반 소지가 있다. 저장소는 공개(GitHub public)다.

## 목표 / 비목표 / 실패 조건

**목표**
1. 카드 혜택 데이터를 `shared/cards.json` 한 파일에 두고, 빌드 전에 자동 검증한다.
2. 카드고릴라 크롤에서 **후보 카드**를 자동 추출하는 조사용 스크립트를 만든다. 결과물은 저장소 밖에 쓴다.
3. 후보 중 카드사 **공식 페이지로 확인한 카드만** 데이터에 넣는다. 항목마다 공식 출처 URL과 확인일을 적는다.
4. 딜 상세 페이지에 "이 판매처 카드 혜택" 섹션을 붙인다. 상품권 결제에 적용되는 카드와 제외되는 카드를 분명히 나눈다.
5. `/cards/` 페이지(쇼핑몰별 카드 혜택 표)와 정적 `api/cards.json`을 만든다.

**비목표(이번 단계에서 하지 않음)**
- 일반 핫딜 수집, 상품명 파서, 상품 묶기(2단계).
- 쇼핑몰 주간 카드 행사 자동 수집, 방문자 카드 저장, 앱(3단계).
- 카드 전체 DB 복제, 카드 검색 페이지.
- Worker API 변경. 카드 데이터는 빌드 시점에 정적으로 넣는다.

**실패 조건(동작해도 실패로 보는 것)**
- 상품권을 제외하는 카드가 상품권 딜에 "혜택 적용"으로 표시되는 것.
- 카드고릴라 문구·이미지·링크가 공개 페이지나 공개 저장소에 들어가는 것.
- 확인일이 없는 카드가 공개되는 것.
- 카드 신청 링크·배너가 생기는 것.

## 제약

- 저장소 관례: `shared/*.json`이 단일 출처(worker·site 공용), 사이트는 `site/scripts/build.mjs`가 템플릿(`{{var}}`, `{{> partial}}`)으로 정적 생성, Tailwind CLI 빌드(D-08), 데이터는 git에 커밋하지 않지만 **설정성 데이터(브랜드·판매처)는 커밋**한다. 카드 혜택 표는 후자에 속한다.
- 파일 줄바꿈은 CRLF(core.autocrlf=true).
- 배포: `main` push → Deploy Site(site/·shared/ 변경 시). 작업은 브랜치에서 하고 전부 검증된 뒤 `main`에 올린다.
- 공개 페이지의 카드 설명은 **우리 표현**으로 쓰고, 카드사 공식 페이지 링크만 건다.

## 데이터 모델 (작성자 결정)

`shared/cards.json`:

```json
{
  "$comment": "쇼핑몰별 카드 혜택. 공식 페이지로 확인한 항목만 status=verified. 카드고릴라 등 제3자 문구 금지.",
  "updated_at": "2026-10-28",
  "stale_after_days": 60,
  "cards": [
    {
      "slug": "shinhan-11st",
      "issuer": "shinhan",
      "name": "11번가 신한카드",
      "type": "credit",
      "annual_fee": "국내 1만원 / 해외 1.2만원",
      "prev_month_min": 300000,
      "official_url": "https://www.shinhancard.com/…",
      "verified_at": "2026-10-28",
      "status": "verified",
      "benefits": [
        { "merchant": "11st", "kind": "discount", "rate": 7, "amount": null, "cap": "월 1만원", "giftcard": "excluded", "note": "11번가 앱 결제 시 즉시할인, 1만원 이상 결제 건" }
      ]
    }
  ]
}
```

규칙:
- `slug` 고유, kebab-case. `issuer`는 `shared/brands.json`의 `card_issuers[].slug`에 있어야 한다. `benefits[].merchant`는 `brands.json`의 `merchants[].slug`에 있어야 한다(없으면 merchants에 먼저 추가).
- `type`: `credit` | `check`. `status`: `verified` | `unverified` | `discontinued`. `verified`만 사이트와 `api/cards.json`에 나온다.
- `kind`: `discount`(할인) | `points`(적립) | `cashback`(캐시백). `rate`(%) 또는 `amount`(원) 중 하나는 있어야 한다.
- `giftcard`: `applies`(상품권 구매에도 적용, 공식 문구로 확인) | `excluded`(상품권 제외, 공식 문구로 확인) | `unknown`(미확인). **기본값은 없다. 반드시 적는다.**
- `official_url`은 `https://`로 시작하고 `card-gorilla.com`을 포함하면 안 된다. `verified_at`은 `YYYY-MM-DD`. `note`는 120자 이하.
- `verified_at`이 `stale_after_days`보다 오래되면 페이지에 "재확인 필요" 표시를 붙이되 숨기지는 않는다.

## 페이지 동작 (작성자 결정)

**딜 상세 `/deal/{id}/`**: "구매 조건" 섹션 아래에 "{판매처} 카드 혜택" 섹션.
- 판매처(`deal.merchant`)가 없으면: "판매처가 확인되지 않아 카드 혜택을 연결하지 못했습니다." 한 줄.
- `giftcard=applies`인 카드가 있으면 목록으로: 카드명(발급사), 혜택 요약(종류·율/금액·한도), 전월실적, 확인일, 공식 안내 링크.
- 없으면: "확인된 카드 중 {판매처}에서 상품권 결제에 혜택을 주는 카드는 없습니다. 대부분의 카드는 상품권·선불충전을 적립·할인에서 제외합니다."
- 접힌 `<details>` "일반 상품 결제 시 혜택 (상품권은 제외)": `excluded`·`unknown` 카드 목록. `unknown`은 "상품권 적용 미확인" 칩.
- 맨 아래 고정 안내: "카드 혜택은 카드사 공식 안내를 기준으로 확인한 값입니다. 혜택 개편이 잦으니 결제 전 카드사 앱에서 다시 확인하세요. 이 사이트는 카드를 모집하지 않습니다."
- 딜 제목에서 뽑은 행사 조건(`deal.card_benefit`)은 기존 "구매 조건"에 그대로 두고 이 섹션에서는 반복하지 않는다. 다만 행사 조건이 있으면 섹션 머리에 한 줄로 "이 딜의 '{행사 조건}'은 판매처 행사 조건(위 구매 조건)이며, 아래의 카드 자체 상시 혜택과는 별개입니다."를 넣어 두 정보가 모순으로 읽히지 않게 한다(리뷰 반영 2026-10-28).

**`/cards/`**: 헤더 메뉴 "카드 혜택". 상품권 제외 원칙을 설명하는 도입 문단, 그 아래 판매처별 섹션(표: 카드 / 혜택 / 월 한도 / 전월실적 / 상품권 구매 시 / 확인일·출처). 카드가 없는 판매처는 섹션을 만들지 않는다. BreadcrumbList JSON-LD. 사이트맵 포함.

**정적 `api/cards.json`**: `verified` 카드만, `benefits[].merchant_name`을 덧붙여 출력. `_headers`의 `/api/*` 규칙을 그대로 적용받는다.

## 조사용 추출 스크립트 (작성자 결정)

`scripts/research/cards-from-crawl.mjs <크롤 api 폴더> [--out <파일>]`
- 폴더의 JSON 중 `url`이 `/v1/cards/{숫자}`로 끝나고 `body.is_discon === false`인 것만, `body.idx`로 중복 제거.
- `brands.json`의 merchants alias로 `top_benefit[].tags/title`과 `key_benefit[].title/comment`를 검색해 판매처별 후보를 만든다. 긴 `info` 본문은 상품권 제외 여부 판정에만 쓴다(`상품권` 근처에 `제외`가 있으면 excluded 추정).
- 추가로 "상품권·충전 긍정 문맥"(충전 캐시백/적립, 상품권 적립/할인 중 제외 문맥이 아닌 것) 후보 목록을 따로 만든다.
- 출력은 Markdown, 기본 경로는 입력 폴더의 상위(`output/..`)에 `candidates.md`. **저장소 안에 쓰지 않는다.** 저장소에 들어가는 것은 코드와 합성 테스트 픽스처뿐이다.
- 내려받은 파일은 JSON.parse로만 읽는다. 데이터 폴더에서 인터프리터를 실행하지 않는다.

## 검증 정책 (작성자 결정)

카드 한 장을 `verified`로 올리는 조건: 카드사 공식 상품 페이지(또는 공식 유의사항 PDF)에서 (1) 해당 판매처 혜택의 종류·율·한도·전월실적, (2) 상품권·선불충전 제외 여부를 읽고 그대로 적었을 때. 확인한 URL을 `official_url`, 날짜를 `verified_at`에 적는다. 확인하지 못한 카드는 `unverified`로 남겨 두고 공개하지 않는다.

1단계 목표 범위: 현재 딜에 등장하는 판매처(지마켓·옥션·11번가·네이버·SSG닷컴·쿠팡·롯데온·카카오톡 선물하기·토스·페이코) 각각 1~3장, 합계 12~20장. 전용 카드(PLCC)를 우선한다.

## 남겨 두는 것(빌더 판단)

- 표의 정렬·칩 색상 등 세부 스타일(기존 `.card`, `.chip`, `.stat` 클래스 재사용).
- 후보 스크립트의 Markdown 표 형식.
- 어떤 카드를 먼저 확인할지(후보 목록의 PLCC 우선 원칙 안에서).

## 이후 단계 메모

- 2단계: 일반 핫딜 파서(상품명·쇼핑몰·가격·배송), 느슨한 상품 묶기, 홈 구조 개편. 이때 `merchants`가 쇼핑몰 사전으로 커진다.
- 3단계: 쇼핑몰 주간 카드 행사(`promotions`, 만료일 필수), 방문자 카드 저장(브라우저 저장), 웹앱.

# 일반 핫딜 수집 확장 설계 (2단계)

작성 2026-11-10. 사용자가 정한 것과 작성자(Claude)가 정한 것을 구분해 적는다. 1단계 설계는 `2026-10-28-card-benefits-design.md`.

## 의도

핫딜 허브의 최종 모습은 "모든 핫딜 + 그 쇼핑몰에서 혜택을 주는 카드"를 보여 주는 정보 사이트다(나중엔 웹앱). 카드 발급 유도와 수수료는 없다. 지금은 커뮤니티 글 중 상품권 딜만 골라 보여 준다. 2단계는 같은 커뮤니티 글에서 **일반 상품 핫딜**도 저장해 보여 주고, 1단계에서 만든 쇼핑몰별 카드 혜택 표를 일반 딜 상세에 붙인다.

## 사용자가 정한 것 (2026-10-28 ~ 11-10 대화)

1. 소스는 지금 그대로다: 뽐뿌, 뽐뿌 쿠폰게시판, 클리앙, 루리웹. 게시판을 추가하지 않는다.
2. 일반 딜은 **전부 저장**한다. 홈에는 점수순 상위만 보여 주고, 전체는 목록 페이지에서 넘겨 본다.
3. 홈의 기본 보기는 **전체 딜**(상품권 + 일반)이고, 탭으로 "상품권만"을 고른다.
4. 벤치마킹 자료(hotdeal.zip 분석, 저장소 밖 `C:\Users\OK\Desktop\블로그이미지\26.11.10 핫딜모음`)에서 얻은 다음 항목을 반영한다: 가격 종류 구분, 판매처 사전 우선순위, 카테고리 열, 결정 기록 D-16 마감.

## 배경 사실

- 뽐뿌·루리웹은 RSS로 받아 **추천·댓글 수가 없다**. 클리앙(HTML)만 있다. 그래서 일반 딜의 인기 신호는 클리앙 추천 수, 여러 커뮤니티에 같은 딜이 올라온 횟수, 최신성이다.
- 벤치마킹 실측(2026-11-10, 300건): 판매처 상위는 G마켓 100, 네이버 39, 쿠팡 33, 11번가 25, 롯데온 19, 토스쇼핑 17, 오늘의집 15, 카카오쇼핑 8, 스팀 5, 옥션 5, 29CM 4. 그쪽은 7개 커뮤니티에서 하루 약 700건이다. 우리 소스 3곳은 하루 250~400건으로 예상한다(추정).
- 그쪽은 가격을 `exact | descriptive | missing`으로 나눠 저장한다. 판매처·카테고리·태그는 글 본문과 서버 처리로 얻는데, 우리는 **제목과 링크만 수집**하므로(출처 정책) 따라 하지 않는다.
- Cloudflare Pages는 배포당 파일 20,000개 한도가 있다. 사이트 빌드는 매시 돌고, 딜 상세마다 API를 한 번씩 부른다.
- 운영 DB(D1)는 이미 데이터가 있다. 배포 워크플로는 매번 `schema.sql`을 그대로 실행한다(`CREATE TABLE IF NOT EXISTS`라 멱등). SQLite의 `ALTER TABLE ADD COLUMN`은 두 번 실행하면 실패한다.

## 목표 / 비목표 / 실패 조건

**목표**
1. 상품권이 아닌 글도 일반 딜(`kind = product`)로 저장한다. 상품권 딜은 `kind = gift`.
2. 제목에서 판매처, 상품명, 가격, 배송비, 카드 조건을 뽑는다. 정규식 1차, 실패 건은 `parse_queue`(D-15).
3. 같은 상품 글을 느슨한 규칙으로 한 딜에 묶는다.
4. 홈을 전체 딜 구조로 바꾸고, 전체 목록 페이지와 일반 딜 상세를 만든다. 일반 딜 상세에 "{판매처} 카드 혜택" 섹션을 붙인다.
5. 공개 API에 `kind` 필터를 넣는다.

**비목표**
- 게시판·커뮤니티 추가, 뽐뿌·루리웹 HTML 수집(추천 수 확보).
- 썸네일 이미지 수집, 글 본문 수집, 최종 이동 주소로 판매처 판별.
- 카테고리 자동 분류, 브랜드·상품 태그, 가격 비교 표, LLM 파싱.
- 판매처 허브 페이지(`/merchants/{slug}/`), 주간 카드 행사, 내 카드 저장, 웹앱(3단계).
- 제휴 링크(D-05 유지).
- hotdeal.zip의 API나 데이터를 수집원으로 쓰는 것.

**실패 조건(동작해도 실패)**
- 기존 상품권 딜의 식별자·dedupe 키·브랜드·액면가 판정이 바뀌는 것. 기존 worker 테스트 33건은 수정 없이 통과해야 한다.
- 상품권 딜이 일반 딜로, 일반 딜이 상품권 딜로 저장되는 것.
- 일반 딜 상세에 "상품권 제외" 칩이 붙어 일반 결제에도 혜택이 없는 것처럼 읽히는 것.
- 벤치마킹 대상의 코드·응답·이미지가 저장소나 사이트에 들어가는 것.
- 운영 DB에 배포할 때 스키마 변경이 두 번째 실행에서 깨지는 것.

## 데이터 모델 (작성자 결정)

`deals` 표를 함께 쓴다. 열을 추가한다.

| 열 | 형식 | 뜻 |
|---|---|---|
| `kind` | TEXT NOT NULL DEFAULT 'gift' | `gift` 또는 `product` |
| `product_name` | TEXT | 일반 딜의 상품명(대괄호·가격 괄호를 뗀 제목). 상품권은 NULL |
| `merchant_raw` | TEXT | 판매처 사전에 없을 때의 원문 표기(예: "하프클럽"). 사전에 있으면 NULL |
| `price_kind` | TEXT | `exact`(숫자 가격) 또는 `descriptive`(가격 다양·무료 등). 상품권은 NULL |
| `price_text` | TEXT | `descriptive`일 때의 원문 표기 |
| `shipping` | TEXT | 정규화한 배송비 표기: "무료", "2,500원", "착불", "조건부 무료", 또는 원문 |
| `product_category` | TEXT | 이번 단계에서는 항상 NULL. 열만 만든다 |
| `title_tokens` | TEXT | 묶기용 정규화 토큰(공백 구분, 정렬됨) |

일반 딜에서 기존 열을 쓰는 방식:
- `brand`는 NOT NULL이라 일반 딜은 `'-'`를 넣는다(dedupe 키의 누락 표기와 같은 관례). `category`는 `'product'`.
- `sale_price`가 가격이다. `face_value`, `buy_rate`, `rate_gap`은 NULL. `discount_rate`는 제목에 "N%"가 있을 때만.
- `card_issuers`, `card_benefit`, `payment_note`, `limit_per_person`은 상품권과 같은 추출 함수를 쓴다.
- `merchant`는 사전 slug, 없으면 NULL이고 `merchant_raw`에 원문.

인덱스: `(kind, status, score DESC)`, `(kind, iso_week, merchant, sale_price)`.

**스키마 변경 방식.** wrangler의 D1 마이그레이션 기능으로 바꾼다. `worker/migrations/0001_init.sql`은 지금의 `schema.sql` 내용 그대로(운영 DB에서는 아무것도 바꾸지 않는다), `0002_product_deals.sql`에 `ALTER TABLE`과 새 인덱스를 둔다. 적용 여부는 wrangler가 DB 안의 기록표로 관리하므로 두 번 실행되지 않는다. `schema.sql`은 새 열까지 포함한 전체 스냅샷으로 갱신해 참고용으로 남긴다. `package.json`의 `db:migrate:*`와 배포 워크플로의 "D1 스키마 적용" 단계를 `wrangler d1 migrations apply`로 바꾼다. 빌더는 로컬 D1에서 "기존 스키마만 있는 DB에 적용"과 "빈 DB에 적용" 두 경우를 모두 확인한다. wrangler가 예상과 다르게 동작하면, 같은 효과(한 번만 실행)를 내는 다른 방법을 골라도 된다.

`shared/sources.json`에 소스별 `kinds` 배열을 둔다. 기본값 `["gift", "product"]`. 뽐뿌 쿠폰게시판은 `["gift"]`(가격 없는 쿠폰 글이 대부분이라 일반 딜로 받지 않고, 큐에도 쌓지 않는다).

## 수집 흐름 (작성자 결정)

`ingestPosts`의 글 한 건 처리 순서:

1. 제외 목록이면 건너뛴다(기존).
2. 상품권 판정(기존 그대로, 종료 표시가 있어도 지금처럼 처리한다): `looksLikeGiftDeal` 통과 → `parseTitle`.
   - 결과가 있고 신뢰도 0.5 이상이면 상품권 딜로 저장한다(기존 경로, 변경 없음).
   - 결과가 있고 신뢰도 0.5 미만인데, 브랜드가 "짧은 alias"가 아닌 것으로 잡혔으면 지금처럼 큐로 보낸다.
   - 그 밖(결과 없음, 또는 짧은 alias로만 잡히고 상품권 단서가 없음)은 3번으로 간다.
3. 소스의 `kinds`에 `product`가 없으면 조용히 건너뛴다. 있으면 아래 순서로 본다.
   - **적립·캐시백·페이백·추첨·응모 이벤트 글**(상품권 파서가 일부러 버리는 글)은 일반 딜로도 받지 않고 큐에도 넣지 않는다. 이 판정을 `parse.ts`에서 함수로 꺼내 두 파서가 같이 쓴다. 상품권 파서의 결과는 달라지지 않는다.
   - **종료 표시 글**(품절·종료·마감·완판): 새 딜을 만들지 않는다. 그 글이 이미 일반 딜에 연결돼 있으면 그 글에 "닫힘" 표시를 한다(아래).
   - 그 밖은 일반 딜 파서를 돌린다. 신뢰도 0.5 이상이면 일반 딜로 저장, 아니면 큐.

2번의 구분을 위해 `parseTitle` 결과에 "짧은 alias로만 잡혔고 상품권 단서가 없음"을 알리는 필드를 하나 더한다. 기존 필드와 값은 그대로다.

**종료 표시는 글 단위로 다룬다.** `deal_posts`에 `closed`(0/1) 열을 더한다. 닫힌 글은 다시 보여도 딜의 `last_seen`을 갱신하지 않고 딜을 되살리지 않는다. 한 딜에 연결된 글이 **모두** 닫히면 그 딜을 바로 `ended`로 바꾼다. 닫히지 않은 다른 커뮤니티 글이 계속 보이면 딜은 진행 중으로 남는다(한 커뮤니티에서만 품절 표시를 단 경우를 과하게 끝내지 않기 위해서다). 닫힌 글의 제목에서 종료 표시가 사라지면 닫힘을 푼다.

**일반 딜의 수명.** 상품권은 지금처럼 24시간 미관측이면 종료 임박, 48시간이면 종료다. 일반 딜은 **12시간 미관측이면 종료 임박, 24시간이면 종료**로 한다. 일반 딜은 빨리 소진되고, 진행 중 딜 수를 하루치(250~400건)로 묶어 두기 위해서다.

**점수 재계산 부담.** 지금은 1분마다 진행 중 딜 전부의 점수를 다시 쓴다. 일반 딜이 들어오면 쓰기가 크게 늘므로, 값이 바뀌지 않은 행은 쓰지 않거나 일반 딜은 10분에 한 번만 다시 계산하는 식으로 줄인다(방법은 빌더 판단).

## 일반 딜 파서 (작성자 결정)

새 파일 `worker/src/parse-product.ts`. 입력은 `RawPost`, 출력은 일반 딜 필드 또는 null.

지원하는 제목 관례:
- 뽐뿌·루리웹: `[쇼핑몰] 상품명 (가격/배송비)`, `[쇼핑몰] 상품명 (가격) (배송비)`, `[쇼핑몰] 상품명 가격 (배송비)`
- 클리앙: `상품명 (쇼핑몰/가격/배송)`, `상품명 가격 (쇼핑몰/배송)`

추출 규칙:
- **판매처**: 맨 앞 대괄호(또는 소괄호) 안의 글자를 사전에서 찾는다. 없으면 끝 괄호의 조각 중 사전에 있는 것을 찾는다. 대괄호가 있는데 사전에 없으면 그 글자를 `merchant_raw`로 보존한다.
- **끝 괄호**: 제목 끝의 괄호 묶음(연속 두 개까지)을 `/`로 나눠 조각마다 판매처·가격·배송비 중 무엇인지 판정한다.
- **가격**: 숫자 가격은 기존 `parseKRW`로 읽는다. 허용 범위 100원 ~ 5,000만원. 끝 괄호 안의 가격을 우선하고, 없으면 본문의 마지막 금액 표기를 쓴다. "다양", "가격다양", "상품별", "무료", "0원" 같은 표기는 `descriptive`로 받고 원문을 `price_text`에 둔다.
- **배송비**: 무료·무배·무료배송 → "무료", 금액 → "N원", 착불, 유료, 조건부 → "조건부 무료", 그 밖은 원문.
- **상품명**: 제목에서 앞 대괄호와 끝 괄호, 가격으로 쓴 금액 표기를 뗀 나머지. 공백을 정리한다. 2자 미만이면 실패.
- **카드·결제·한도**: 상품권 파서의 추출 함수를 공용으로 꺼내 같이 쓴다.

신뢰도: 기본 0.3, 판매처(slug 또는 원문) +0.2, 숫자 가격 +0.35, 서술형 가격 +0.25, 배송비 +0.1, 상품명 토큰 2개 이상 +0.05. 가격이 전혀 없으면 0.45를 넘지 못해 큐로 간다.

## 같은 상품 묶기 (작성자 결정, D-19로 기록)

완벽한 상품 식별이 아니라 "같은 글이 여러 커뮤니티에 올라온 것"을 잡는 것이 목적이다.

1. 같은 커뮤니티 글(`source`, `post_id`)은 항상 처음 연결된 딜에 붙는다. 제목이 나중에 바뀌어도 새 딜을 만들지 않는다.
2. 새 글은 **같은 주차** 안에서, **같은 판매처**(slug, 없으면 정규화한 원문 표기)이고 **같은 가격**이며 종료되지 않은 일반 딜을 후보로 찾는다. 후보 중 제목 토큰 집합의 Jaccard 유사도가 **0.5 이상**인 것 가운데 가장 높은 딜에 붙인다.
3. 후보가 없으면 새 딜을 만든다. 키는 `product|판매처키|가격|토큰 해시|주차`, 식별자는 기존처럼 키의 SHA-1 앞 16자.
4. 판매처를 전혀 모르는 글, 서술형 가격인 글은 토큰이 완전히 같을 때만 묶는다(3번의 키가 같아지는 경우).
5. 가격이 다르면 다른 딜이다. 가격 변동 추적은 이번 범위가 아니다.

토큰 정규화: 앞 대괄호와 끝 괄호를 뗀 상품명을 소문자로 바꾸고, 한글·영문·숫자가 아닌 글자를 공백으로 바꿔 나눈다. 1글자 토큰과 흔한 말(무료배송, 무배, 특가, 핫딜, 할인, 쿠폰, 역대가, 최저가, 카드 등)은 버린다. 중복을 없애고 정렬한다.

유사도 계산과 토큰화는 순수 함수로 `worker/src/group.ts`에 두고 테스트한다. 기준값 0.5는 운영 2주 뒤 실제 묶인 결과를 보고 조정한다.

상품권 딜의 dedupe(D-02)는 바꾸지 않는다.

## 점수 (작성자 결정)

기존 산식에 "등장 커뮤니티 수" 항을 더한다: 2곳이면 +0.1, 3곳 이상이면 +0.2. 상품권에도 같이 적용된다(여러 곳에 올라온 딜을 올려 주는 방향이라 순서가 크게 바뀌지 않는다). 일반 딜은 할인율이 대개 없어 최신성, 클리앙 추천 수, 등장 커뮤니티 수로 순서가 정해진다. 운영 2주 뒤 보정한다(D-10).

## 공개 API (작성자 결정)

- `GET /api/deals.json`에 `kind=all|gift|product`. **기본값은 `all`**. `merchant=slug` 필터 추가. `limit` 상한을 200에서 500으로 올리고 `offset`을 추가한다(응답에 `has_more`). 빌드는 진행 중 딜을 `has_more`가 없을 때까지 이어 받는다.
- 빌드의 종료 딜 조회는 종류별로 나눈다: 상품권 종료 딜(지금처럼 최근 200건), 일반 종료 딜(종료 3일 이내만 필요하므로 최근 500건). 일반 딜이 상품권 종료 딜 상세를 밀어내면 안 된다.
- `brand` 파라미터나 `/api/brands/{slug}.json`은 자연히 상품권만 나온다.
- `/api/weekly/{주차}.json`은 상품권만 돌려준다(주간 비교는 상품권 기능).
- 딜 응답에 `kind`, `product_name`, `merchant_raw`, `price_kind`, `price_text`, `shipping`, `product_category`, `sources`(등장 커뮤니티 slug 배열)를 더한다. 일반 딜의 `brand_name`은 null.
- 딜 상세의 "과거 반복"은 상품권만 계산한다. 일반 딜은 빈 배열.
- `/api/status.json`에 종류별 활성 딜 수를 더한다.
- 임베드 위젯은 상품권 전용으로 남긴다. 위젯이 API를 부를 때 `kind=gift`를 붙이고, 정적 사본을 읽을 때는 `kind`로 걸러 낸다.
- `/open-data/` 문서에 새 파라미터와 "기본값이 전체로 바뀜"을 적는다.

## 사이트 (작성자 결정)

**홈 `/`**
- 히어로 문구를 전체 핫딜 + 카드 혜택 중심으로 바꾼다. 상품권 상테크 설명은 아래 안내 구역에 남긴다.
- 탭 세 개: 전체(기본) / 상품권 / 일반. 화면 안에서 걸러 낸다(페이지 이동 없음).
- 보여 주는 딜: 진행 중인 딜 중 점수순 상위 60건. 진행 중인 상품권 딜은 60건에 못 들어도 모두 포함한다(상품권 탭이 비지 않게).
- 필터: 판매처(목록에 있는 것만), 상태, 카드 조건. 브랜드 필터는 상품권 탭에서만 보인다.
- 목록 아래에 "전체 딜 보기" 링크.

**전체 목록 `/deals/`** (새 페이지)
- `/deals/`(전체), `/deals/gift/`, `/deals/product/`. 진행 중인 딜을 최신순으로 50건씩, 2쪽부터 `/deals/2/`, `/deals/product/2/` 형태. 이전·다음 링크.
- 헤더 메뉴: 홈 / 전체 딜(`/deals/`) / 상품권 브랜드(`/brands/`) / 주간 비교 / 카드 혜택 / 데이터 제공 / 소개.

**일반 딜 카드** (새 partial)
- 판매처(없으면 원문 표기, 그것도 없으면 "판매처 미확인") · 상품명 · 가격(서술형이면 원문) · 배송비 · 카드 조건 칩 · "N곳에 올라옴" 칩(2곳 이상일 때) · 출처 커뮤니티 · 상세 링크.
- 상품권 카드는 지금 모양 그대로.

**일반 딜 상세 `/deal/{id}/`** (새 템플릿)
- 상단: 판매처, 상태, 상품명, 최초 발견·마지막 확인.
- 수치: 가격 / 배송비 / 판매처 / 커뮤니티 반응.
- "구매 조건": 카드 조건, 결제 조건, 1인 한도, 배송비. 자동 추출 안내 문구는 기존과 같다.
- **"{판매처} 카드 혜택" 섹션**: `renderDealCardSection`에 종류를 넘겨 일반 딜용으로 그린다(아래).
- 출처 커뮤니티 글, 일별 기록, "같은 판매처 다른 딜"(옆 칸).
- 구매 버튼은 원문 글로 간다. 종료 딜은 버튼을 끄고 "같은 판매처 진행 중 딜"(`/deals/product/`)로 안내한다.
- 종료 딜은 noindex. **일반 딜 상세는 종료 후 3일까지만 만든다**(상품권은 D-07의 30일 그대로). 3일이 지난 일반 딜을 가리키는 **사이트 내부 링크**는 `/deals/product/`로 건다. 밖에서 들어온 옛 주소는 기존 404 안내 페이지가 받는다(리다이렉트는 만들지 않는다).
- JSON-LD는 `Offer`(가격이 숫자일 때만 price)와 BreadcrumbList.

**일반 딜의 카드 혜택 표시 문구**
- 머리: "{판매처} 카드 혜택". 딜에 카드 행사 조건이 있으면 1단계의 "별개입니다" 한 줄을 그대로 쓴다.
- 도입 한 줄: "{판매처}에서 일반 상품을 결제할 때 혜택을 주는 카드입니다. 전월 실적과 월 한도를 함께 확인하세요."
- 그 판매처의 verified 카드를 **전부 본문 목록**으로 보여 준다. 접힌 목록을 쓰지 않는다. 정렬은 혜택률 높은 순, 그다음 카드명.
- 카드 행에 상품권 칩(적용/제외/미확인)을 **붙이지 않는다**. 혜택 설명(`note`)은 그대로 보여 준다(상품권 제외 문구가 들어 있어도 사실이므로 둔다).
- 카드가 없으면: "확인된 카드 중 {판매처}에서 혜택을 주는 카드가 아직 없습니다."
- 판매처가 사전에 없으면: "이 판매처({원문 표기})는 아직 카드 혜택 표에 없습니다." 판매처를 전혀 모르면 1단계 문구 그대로.
- 맨 아래 고정 안내(`CARD_NOTICE`)는 그대로.
- 상품권 딜의 섹션은 1단계 동작에서 한 글자도 바뀌지 않는다(site 테스트 9건 유지).

**그 밖**
- 주간 비교, 브랜드 허브, 임베드는 상품권 전용으로 남는다.
- 소개 페이지의 사이트 설명과 수집 범위 문구를 일반 핫딜까지 포함하도록 고친다.
- 사이트맵에 `/deals/` 목록들과 진행 중인 일반 딜 상세를 넣는다.
- 정적 `api/deals.json`은 진행 중인 전체 딜.
- 빌드는 딜 상세 API를 동시에 6개까지 부른다(지금은 하나씩).

**샘플 데이터**: `site/data/sample.deals.json`에 일반 딜을 4건 이상 넣는다. 카드 혜택 표에 있는 판매처 1건(쿠팡 등), 사전에 없는 판매처 1건, 서술형 가격 1건, 두 커뮤니티에 올라와 묶인 1건, 종료 1건을 포함한다. `sample.details.json`에도 맞춰 넣는다. 테스트 픽스처는 지어낸 제목을 쓴다(벤치마킹 자료에서 복사하지 않는다).
